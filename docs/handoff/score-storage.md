# 成绩存储与升级交接

更新：2026-09-30。本文件记录工单 04 第三阶段的数据结构、校验、升级和备份兼容。第四阶段后台确认、幂等、差异和历史已实现，见 [确认与历史交接](score-confirmation.md)。完整成绩界面尚未接入，不能将后台测试当成整单交付。

## 数据结构

Schema 2 保留原有名册、班级归属和附件表，增加：

- `exams`：稳定考试 ID、班级 ID、创建时间。
- `score_versions`：稳定版本 ID、考试 ID、递增版本号、唯一请求 ID、请求摘要、时间、更正原因及完整版本内容。

版本内容采用严格验证的 JSON：原始分口径确认、考试名称、日期、学年学期和年级；科目、满分、计分组；当时的应考名册身份和姓名；四种成绩状态；导入文件摘要、名称、列映射和排除原因。数据量有界、按版本整体读取，避免为每次历史查看拼装分散的当前配置。JSON 不接受任意扩展字段，格式由 `src/shared/score-records.ts` 定义。

统计结果不另存一份可能失真的数值，按版本内完整输入确定性计算。学生或班级后续改名不改写旧版本。第四阶段的 `ScoreBook` 写入接口只追加版本，不提供修改或删除旧版的接口；备份验证另拒绝无确认版本的孤立考试。阅卷确认入分须在后续工单扩展来源契约，不应伪装成 CSV 导入。

## 升级与恢复

1. 对 v1 校验版本、应用标识、完整 SQL 白名单、SQLite 完整性和名册语义；工作区启动还须先验证附件完整性。不接受额外触发器、视图或损坏数据。
2. 正式可写打开时，使用 `VACUUM INTO` 在原数据库旁保存 `data.sqlite.before-v2-<UUID>.sqlite`。失败则停止升级，不能跳过副本继续。
3. 同一事务中创建新表、写版本号并再次验证，成功才提交。异常或提交前进程退出由 SQLite 回滚，不留下部分新结构。
4. 只读打开不迁移。旧备份预览始终保留原始字节；教师确认恢复后，迁移独立恢复副本，再发布工作区入口。
5. 新备份声明协议 v2；仍读取 v1。声明版本必须与内部数据库 Schema 一致，不能把新库标成旧格式。

升级前副本仅包含数据库；附件未被升级修改，仍在相邻 `assets` 目录。它是维护恢复材料，不是包含附件的 `.cmbackup` 文件。普通用户升级前仍应通过程序导出完整备份。不要把独立 SQLite 副本重命名成 `.cmbackup` 或直接改版本号。此阶段没有新增“回退数据库升级”按钮。

## 配额与验证

统一上限位于 `src/core/storage-limits.ts`：数据库 64 MiB、备份 128 MiB、单成绩版本 JSON 40 MiB、1000 场考试、2000 个成绩版本。单版本上限计入历史名册的中文姓名，不能只按上传文件大小估算。附件原有限制不变。可写连接设置 SQLite 页数上限，避免继续写大到无法重新打开；迁移与备份也校验容量。各上限同时生效，不承诺保存 2000 份满容量版本。后续业务写入仍须在事务内检查考试/版本数量，并将容量失败显示为明确错误，不能丢弃历史腾位置。

导入备份时逐个验证版本内容及引用，拒绝无效 JSON、非法成绩、未知学生、非连续版本链或倒退的版本时间；当前学生姓名不用于覆盖历史名称。SHA-256 只验证完整性，不证明来源可信，不能替代语义校验。

`tests/database-migration.test.ts` 使用冻结 v1 SQL 建表文本，避免用当前建表器制造“旧库”。覆盖只读不改写、一次升级、保留旧副本、未知结构与坏名册拒绝、异常回滚、真实子进程退出恢复、v1 备份预览/确认升级、v2 标识校验、历史版本往返及伪造正确哈希的坏成绩拒绝。全部仅使用合成数据。

本阶段验证：23 项迁移/存储测试通过；全仓 144 项测试、格式、类型、Lint 和构建通过。10000 人、20 科、最长中文姓名的 200000 条成绩已完成真实 SQLite 写入、完整备份、恢复和重新读取。边界流程保留 30 秒测试门槛；发现归属查询缺少索引后，在 Schema 2 中增加 `enrollment_history(student_id)`，没有通过放宽门槛掩盖超时。此为本机合成测试，不是其他设备的速度保证。

Standards/Spec 双路自审发现并修复了：附件检查晚于迁移、崩溃测试提前使用裸连接恢复、来源映射语义不完整。两路复审确认闭环，未发现本阶段新增明确阻塞。数据库版本、备份容量、历史记录与新索引均纳入复审；整个工单 04 尚未验收。
