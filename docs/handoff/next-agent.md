# 后续执行与审计交接

用户安排：后续功能由其指定的执行模型继续，当前助手负责后续审计。本文件不发起其他模型调用，不表示后台会自动审计。

## 接手流程

1. 读取根目录 README、`docs/handoff/m0-verification.md`、`docs/handoff/developer.md`，先运行现有检查。完成条件：记录实际环境、基线检查结果及已有失败，不将新增失败归给“原来如此”。
2. 读取 `docs/planning/tickets.md` 和本次用户指定的单张工单。建议接下来的本地业务工单为 04 成绩导入，或按用户选择先做 03 模型设置；每次只做一个可验收流程。完成条件：范围、依赖和验收项清楚，涉及未知业务决策时记录问题。
3. 修改前保留基线，按模块实现并补测试。完成条件：M0 名册、IPC 隔离、坏备份拒绝、恢复回退和重开测试仍通过；新增能力有正常与失败验证。
4. 更新对应手册、规格及工单状态。完成条件：没有未实现按钮冒充完成，没有把测试替身标成真实模型/设备成功。
5. 提交审计包给用户。完成条件：改动文件、需求对应、实际命令与结果、界面证据、数据兼容性、未验证项及已知问题齐全。

## 稳定基线

当前仓库尚未建立 Git 提交基线，工作文件不可随意清理或回退。`scripts/freeze-baseline.mjs` 用于一次性保存源码原文与 SHA-256 清单，生成位置为 `output/m0-baseline/`。该输出默认不进 Git，迁移工作环境时应一并保留。

基线生成后再次执行会拒绝覆盖。审计以冻结原文或后续由用户建立的明确 Git commit 为对照，不以可被修改的“测试通过”描述代替证据。改动后不要重写 M0 冻结基线。

## 必须保留的规则

- 同一学生身份贯穿模块；实体 revision 与恢复 epoch 继续阻止陈旧写入。
- 只有受限具名接口跨 Renderer/Main；系统权限、数据库及密钥不进入 Renderer。
- 数据库写入和附件管理保持串行、一致；扩表同时处理 Schema、迁移与备份兼容。
- 未知结构/坏备份停写，保留原数据；不会通过重建空库或跳过哈希“修复”问题。
- 模型内容和上传资料作为数据处理；正式成绩和档案需教师确认。
- 使用合成资料测试。密钥以后通过本地设置输入，代码、聊天、日志、测试证据与备份不包含完整 Key。

## 交回审计的清单

| 项目 | 内容 |
| --- | --- |
| 范围 | 工单号、实现/未实现验收项、涉及模块 |
| 变更 | 文件清单或明确 Git diff，设计偏离及理由 |
| 数据 | Schema/备份版本、旧数据升级与回退证据 |
| 检查 | 格式、类型、Lint、核心测试、桌面/打包测试的实际输出 |
| 外部能力 | mock 与真实接口分开，服务商/模型、样本范围和用量 |
| 界面 | 桌面与窄窗口截图、取消/错误/恢复状态 |
| 风险 | 未验证环境、遗留缺陷、人工接手步骤 |

审计将优先检查数据损坏、重复写入、审核绕过、密钥泄露、IPC 越权、导出/备份兼容性和测试缺口。通过审计不自动代表完成真实业务试点或客户验收。
