# 正常功能提问的对话容量修复

2026-10-04：用户在业务对话中发送“你还有什么功能？”，看到 `VALIDATION` 和“输入不符合要求，请检查内容和版本”。本次修复同类错误；保留 `business-agent-v7` 协议与确认后自动继续规则。

## 证据与诊断

截图表明任务在本地输入校验中停止，单凭截图不能定位具体校验字段。只读核对用量账本的时间、状态和协议，不读取模型密钥或对话正文：最近 v7 模型调用成功，没有对应的新失败调用。这符合 `agentRequest()` 在用量记录与联网前调用 `previewConversation()`，在本地失败的路径。账本不保存消息条数，因此不将其当作截图任务的完整调用追踪。

新增真实 Runner 回归场景：同一会话先问候，再发送用户原句，不选择班级/学生；模型按 8 项一批读取 87 个具名功能的参数说明，随后正常回答。业务仅执行 `snapshot` 读取，没有正式写入。旧版稳定失败，报 `ZodError / too_big / maximum: 100 / path: []`，位置为 `DeepSeekClient.conversationBody()`；经 `publicError()` 映射后就是截图中的通用 `VALIDATION` 提示。

由于单轮已支持 16 次模型往返、每次最多 8 个原生工具，最多产生 16 条 assistant 消息与 128 条工具回执；加上至多 48 条保留历史、系统规则和用户请求，最大正常预算为 194 条。旧版最多 100 条的限制与 Agent 已声明的能力不一致。正常用户提问并非必须自行修改的非法输入。

## 修复

- 传输消息上限调整为 200，覆盖完整 194 条预算，保留原工具调用校验和配对历史。
- 消息数量超过 200 或上下文超过 1 MiB 时返回明确的 `CONVERSATION_CONTEXT_LIMIT` 和容量提示，不再把容量问题误写为用户输入错误。
- 16 次模型往返、每批最多 8 项工具、查询去重、正式操作逐项确认、成功回执不重放、脱敏与字节预算继续生效。
- 没有自动重试网络、使用真实账号、覆盖用户安装或修改用户数据库。
